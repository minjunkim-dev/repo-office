# 설계 단계

이 단계 하나만 한다. 제품 코드는 `repo/`에 있다(작업 폴더는 과제 폴더다). push·`gh pr merge`·`gh pr edit`·`gh api` 쓰기는 거부된다. 엔진이 이 단계를 다시 띄웠으면 `{job}/INTENT.md`와 이 지시서를 다시 읽는다. leader가 막힌 일의 답을 `INTENT.md` 결정 기록에 적었을 수 있다.

- 읽을 것: `{job}/INTENT.md`, `{job}/repo/`의 코드와 `AGENTS.md`.
- 쓸 것: `{job}/design.md` 하나. 다 쓰면 끝낸다.
- `design.md`에는 다음을 적는다.
  - 완료 기준: 무엇이 되면 끝인지, 무엇이 깨지면 안 되는지. PR 본문 Summary의 `완료 기준:` 줄에 그대로 쓸 한 줄.
  - 바꿀 파일과 이유.
  - 되돌리기 쉬움·어려움과 그 근거. 애매하면 어려움이다. 판정은 `되돌리기: 쉬움` 또는 `되돌리기: 어려움` 한 줄로 그대로 쓴다. 승인된 설계와 PR 본문이 둘 다 쉬움이면 리뷰는 sonnet으로 돈다. 아니면 opus이고, 소유자가 diff를 읽고 병합한다.
  - 확인하지 않을 범위.
  - 난이도 한 줄: `난이도: 쉬움`, `난이도: 보통`, `난이도: 어려움` 중 하나를 그대로 쓴다. 쉬움은 문서만 바꾸기, 코드 몇 줄, 테스트만 더하기, 이름 바꾸기다. 새 동작이나 여러 파일에 걸친 변경은 보통, 민감한 파일·되돌리기 어려운 변경은 어려움이다. 이 설계는 opus로 돈다. 엔진은 승인된 이 줄로 구현 작업자의 모델을 고른다(쉬움이면 haiku, 그 밖이면 sonnet). 사람의 설계 승인이 이 줄의 확인이다.
  - 테스트할 seam: 테스트할 공개 인터페이스와, 각각이 잡는 것·놓치는 것을 한 줄씩. 구현 단계는 이 목록 밖에서 테스트를 쓰지 않는다. 사람의 설계 승인이 이 목록의 확인이다.
- 모듈 경계나 인터페이스 모양을 정해야 하면 `mattpocock-skills:codebase-design` 스킬을 참고로 부른다. 스킬 이름은 앞 이름까지 다 쓴다.
- 코드는 고치지 않는다. 사람이 설계를 승인하기 전이다.
- 보고 메시지·배포·push·다른 과제 폴더 수정은 하지 않는다.
- 막히면 지어내지 말고 `{job}/BLOCKED.md`에 이유를 적고 끝낸다.
- 끝낼 때는 `{job}/design.md`나 `{job}/BLOCKED.md` 중 하나를 반드시 쓴다. 앞 라운드에서 이미 끝난 일이어도 이번 결과를 새로 쓴다. 둘 다 없으면 엔진은 실패로 센다.
